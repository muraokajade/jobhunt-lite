# セクション7：CompanyTable分割・実用UI化 実装順序メモ

## 目的

セクション6では、検索・絞り込み機能を実装した。

セクション7では、検索・絞り込みまで終わった企業一覧を、`CompanyTable` コンポーネントに切り出し、実用的な一覧UIに育てる。

このセクションの目的は、単に見た目を整えることではない。

目的は以下。

- `App.tsx` にベタ書きしていた企業一覧を分離する
- 一覧表示の責務を `CompanyTable` に移す
- API通信や state 管理は親の `App.tsx` に残す
- 子コンポーネントは props で受け取ったデータを表示する
- 子コンポーネントは props で受け取った関数を呼び出す
- 詳細・削除・志望度変更・状況変更・favorite・落選表示・もっと見るを段階的に追加する

---

# セクション6とセクション7の位置づけ

## セクション6：検索・絞り込み機能

### 目的

CRUD の一覧表示を、keyword / status / media で探せる実用的な一覧にする。

### 主役

- `SearchForm`
- `fetchCompanies`
- `URLSearchParams`
- Laravel の `index(Request $request)`
- GET クエリパラメータ
- `keyword`
- `status`
- `media`

### セクション6で理解すること

- 検索は POST ではなく GET
- `Request $request` は GET でも使える
- React 側で検索条件を URL に付ける
- Laravel 側で `$request->query()` から検索条件を受け取る
- Laravel 側では `$query` に条件を積み上げる
- 最後に `get()` して検索結果を取得する

### 目的

検索・絞り込みまで終わった企業一覧を、`CompanyTable` コンポーネントに切り出し、実用的な一覧UIにする。

### 主役

- `onOpenDetail`
- `onDelete`

- `isRejected`

# 完成形の方向性

完成形では、親の `App.tsx` から `CompanyTable` に以下を渡す。

    <CompanyTable
      companies={companies}
      loading={loading}
      priorityOptions={priorityOptions}
      statusOptions={statusOptions}
      onPriorityChange={updateCompanyPriority}
      onStatusChange={updateCompanyStatus}
      onOpenDetail={openDetailModal}
      onDelete={deleteCompany}
      onToggleFavorite={toggleCompanyFavorite}
    />

この形を見ると、`CompanyTable` は自分で API 通信をしていない。

`CompanyTable` は、親から受け取った以下を使う。

- 表示用データ
- 読み込み状態
- select の選択肢
- 詳細ボタン押下時の関数
- 削除ボタン押下時の関数
- 志望度変更時の関数
- 状況変更時の関数
- favorite切り替え時の関数

---

# 最重要の考え方

## CompanyTable は API 通信を担当しない

`CompanyTable` は一覧表示の部品。

API通信は親の `App.tsx` が担当する。

つまり、責務はこう分ける。

    App.tsx
    - companies stateを持つ
    - API通信をする
    - fetchCompaniesを持つ
    - deleteCompanyを持つ
    - updateCompanyPriorityを持つ
    - updateCompanyStatusを持つ
    - toggleCompanyFavoriteを持つ
    - openDetailModalを持つ

    CompanyTable.tsx
    - companiesを表示する
    - loading中の表示を出す
    - 0件表示を出す
    - 詳細ボタンを表示する
    - 削除ボタンを表示する
    - selectを表示する
    - favoriteボタンを表示する
    - ボタンやselect操作があったら親から受け取った関数を呼ぶ

---

# このセクションの重要な理解

    CompanyTableはAPI通信を担当しない。
    App.tsxがstateとAPI通信を担当する。
    CompanyTableは、親から受け取ったcompaniesを表示する。
    CompanyTableは、ボタンやselect操作があったら親から受け取った関数を呼ぶ。
    子コンポーネントは「どの企業に対して操作したか」を親に伝える。

# Step 3：loading と 0件表示を入れる

## やること

- `loading: boolean` を props に追加する
- `loading` が true なら「読み込み中...」を表示する
- `companies.length === 0` なら「企業データがありません。」を表示する

## loading表示の意味

API通信中は、まだデータが取得できていない。

その状態で何も表示されないと、ユーザーは以下のどちらか分からない。

- 読み込み中なのか
- 本当にデータがないのか
- エラーなのか

そのため、loading表示を入れる。

## 0件表示の意味

API通信は成功したが、企業データが0件の場合に表示する。

## 理解度チェック

    Q. loading表示と0件表示はなぜ必要か？

    A. API取得中なのか、本当にデータがないのかをユーザーに伝えるため。

# Step 4：詳細ボタンを接続する

## やること

- `onOpenDetail: (company: Company) => void` を props に追加する
- 詳細ボタンを作る
- 詳細ボタンで `onOpenDetail(company)` を呼ぶ

## 重要な書き方

    onClick={() => onOpenDetail(company)}

この書き方にする。

## ダメな書き方

    onClick={onOpenDetail(company)}

これはダメ。

理由は、画面表示時に即実行されるから。

クリックされた時だけ実行したいので、アロー関数で包む。

## 理解度チェック

    Q. なぜ company を渡すのか？

    A. どの企業の詳細を開くのか親に伝えるため。

    Q. なぜ onClick={() => onOpenDetail(company)} と書くのか？

    A. クリックされた時だけ実行したいから。
       onClick={onOpenDetail(company)} だと描画時に即実行される。

# Step 5：削除ボタンを接続する

## やること

- `onDelete: (id: number) => void` を props に追加する
- 削除ボタンを作る
- 削除ボタンで `onDelete(company.id)` を呼ぶ

## 書き方

    onClick={() => onDelete(company.id)}

## なぜ id だけ渡すのか

削除APIは以下の形で対象を指定する。

    DELETE /api/companies/{id}

そのため、削除処理では `company` 全体ではなく、`id` だけでも十分。

## 理解度チェック

    Q. 削除はcompany全部ではなくidだけでもよい理由は？

    A. DELETE APIは /companies/{id} で対象を指定できるから。

# Step 6：志望度 select を表示する

## やること

- `priorityOptions` を props で受け取る
- 志望度 select を表示する
- `company.priority` を select の value にする

## まだやらないこと

この段階では、DB更新処理を重く考えない。

まずは select が表示されることを確認する。

## priorityOptions を props で渡す理由

選択肢を `CompanyTable` 内にベタ書きしないため。

選択肢はアプリ全体で使う可能性がある。

そのため、外部の constants で管理し、props で渡す。

## 理解度チェック

    Q. priorityOptionsをpropsで渡す理由は？

    A. 選択肢をCompanyTable内にベタ書きせず、外で共通管理するため。

# Step 7：志望度変更を親に通知する

## やること

- `onPriorityChange: (company: Company, priority: string) => void` を props に追加する
- select の `onChange` で `onPriorityChange(company, event.target.value)` を呼ぶ

## なぜ company も渡すのか

新しい priority だけ渡しても、どの企業の志望度を変更するのか分からない。

そのため、対象企業の `company` と、新しい値である `priority` の両方を渡す。

## 書き方

    onChange={(event) =>
      onPriorityChange(company, event.target.value)
    }

## 理解度チェック

    Q. なぜ priority だけでなく company も渡すのか？

    A. どの企業の志望度を変更するのか分からないから。

    Q. selectを変更しただけでDBは更新されるのか？

    A. されない。
       親のonPriorityChangeの中でAPI通信を行って初めてDBが更新される。

---

# Step 8：状況 select も同じ形で作る

## やること

- `statusOptions` を props で受け取る
- `onStatusChange` を props で受け取る
- 状況 select を表示する
- select の `onChange` で `onStatusChange(company, event.target.value)` を呼ぶ

## 考え方

これは志望度 select の横展開。

構造は同じ。

    selectの値が変わる
    ↓
    対象companyと新しい値を親へ渡す
    ↓
    親側でAPI通信する
    ↓
    一覧を再取得する

## 理解度チェック

    Q. priority変更とstatus変更は構造的に何が同じか？

    A. selectの値を変えたら、対象companyと新しい値を親へ渡す点。

# Step 9：favorite は最初は文字ボタンでやる

## やること

- `onToggleFavorite: (company: Company) => void` を props に追加する
- favorite切り替え用のボタンを置く
- 最初は SVG にしない
- 最初は文字ボタンで動作確認する

## 表示例

    isFavorite が false なら「お気に入り」

## なぜ最初は文字ボタンにするのか

まずは以下を理解する。

    CompanyTableから親へcompanyを渡す
    ↓
    親側でPATCH APIを叩く
    ↓
    一覧を再取得する

## 理解度チェック

    Q. favoriteのAPI通信はCompanyTableでやるべきか？

    A. まずは親App.tsxでやる。
       CompanyTableは押されたことを伝えるだけ。

# Step 10：文字ボタンをハートSVGに置き換える

## やること

- 文字ボタンを SVG のハートに置き換える
- `company.isFavorite` に応じて塗りつぶしを切り替える

## SVGの考え方

    fill={company.isFavorite ? "currentColor" : "none"}

お気に入り済みなら中身を塗る。

お気に入りでなければ中身を塗らず、線だけにする。

## 理解度チェック

    Q. fill="none" の時はどう見えるか？

    A. 中身が塗られず、線だけのハートになる。

    Q. fill="currentColor" の時はどう見えるか？

    A. 現在の文字色と同じ色で中身が塗られる。

# Step 11：お気に入り行の見た目を変える

## やること

- `company.isFavorite` が true の行だけ背景色を変える
- 会社名横に「注目」チップを出す

## 目的

favorite は単にハートを切り替えるだけではない。

本命企業・注目企業が一覧上で分かりやすくなることが重要。

## 考え方

    isFavorite が true
    ↓
    ハートが塗られる
    ↓
    行の背景色が変わる
    ↓
    会社名横に注目チップが出る

## 理解度チェック

    Q. favoriteはDBの値か、フロントだけの見た目か？

    A. DBのis_favoriteをAPI経由で更新し、その結果をUIに反映している。

# Step 12：落選行の見た目を変える

## やること

- `const isRejected = company.status === "落選";` を作る
- 落選なら行を薄くする
- 会社名に `line-through` を入れる
- 落選チップを出す

## なぜ落選企業を薄く表示するのか

落選企業は削除する必要はない。

落選企業には、振り返り・分析ログとして価値がある。

ただし、現在対応中の企業と同じ見た目だとノイズになる。

そのため、データとして残しつつ、一覧上では視覚的に弱める。

## 理解度チェック

    Q. なぜ落選企業を削除せず、薄く表示するのか？

    A. 落選企業も振り返り・分析ログとして価値があるから。
       ただし現在対応すべき企業ではないので、一覧上では視覚的に弱める。

---

# Step 13：favorite と落選の優先順位を決める

## やること

favorite と落選が両方 true になり得る場合、どちらの見た目を優先するか決める。

完成品では、落選を優先する。

## 優先順位

    落選なら赤・薄め
    落選でなければfavoriteなら注目表示
    どちらでもなければ通常表示

## なぜ落選を優先するのか

favorite だった企業でも、落選した後は現在対応中の企業ではない。

そのため、注目企業として目立たせるより、落選済みとして視覚的に弱める方が自然。

## 理解度チェック

    Q. favoriteかつ落選の場合、どちらの見た目を優先するか？

    A. 落選を優先する。
       現在対応対象ではないため。

    isExpanded = true

## 表示対象

## ボタン表示条件

    const shouldShowMoreButton = companies.length > 5;

## 理解度チェック

    Q. もっと見るはDBから追加取得しているのか？

    A. していない。
       すでに取得済みのcompaniesから表示件数だけ変えている。

# セクション7終了時に説明できるようになりたいこと

セクション7が終わったら、以下を自分の言葉で説明できる状態にする。

    CompanyTableは一覧表示を担当する子コンポーネント。
    App.tsxはstate管理とAPI通信を担当する親コンポーネント。
    子コンポーネントはpropsでcompaniesを受け取る。
    子コンポーネントはpropsで関数を受け取り、クリックや変更イベントで親に通知する。
    どの企業を操作するか分かるように、companyやidを親へ渡す。
    select変更だけではDBは更新されない。

    favoriteはCompanyのis_favoriteを更新し、UIに反映する。
    落選企業は削除せず、学習ログとして残しつつ視覚的に弱める。
    もっと見るはDB再取得ではなく、フロント側の表示件数切り替え。
